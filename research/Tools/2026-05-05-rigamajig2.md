# Rigamajig2 — Data-Centric Modular Rigging System

## Descripción
Rigamajig2 es un sistema de rigging modular y orientado a datos para Autodesk Maya, desarrollado por Mason Smigel. Su premisa central es que el rig entero es reconstruible desde archivos JSON, eliminando la dependencia de escenas guardadas. Cada componente es autocontenido e interoperable con los demás, y el sistema expone un framework Python extensible para componentes custom.

## Stack técnico
- Language: Python 3.9+
- Platform: Autodesk Maya (versión no especificada; última release v1.3.2, agosto 2024)
- UI: PySide2 (BuilderUI)
- Code quality: Black, Pylint, Pytest + mayatest

## Detalles técnicos

### Arquitectura central
- **Data-centric**: la totalidad del rig se exporta y reconstruye desde archivos JSON. No hay "escena maestra" del rig; sólo datos + código.
- **Archetypes**: templates de componentes reutilizables. Un archetype define la configuración por defecto de un componente (p.ej. brazo bípedo, columna ribbon, etc.).
- **Component interface**: cada componente recibe inputs a través de un único nodo de interfaz; los componentes se conectan entre sí via estas interfaces. Arquitectura similar a "black boxes" con contratos de I/O definidos.
- **Three interfaces**:
  - *Author Interface*: framework Python para crear/extender componentes.
  - *Rigger Interface* (BuilderUI): construir rigs usando componentes y archetypes existentes.
  - *Animator Interface*: rig entregable con picker de controles e IK/FK match integrado.

### Pipeline de build
1. Definir guides (objetos proxy en escena).
2. Exportar configuración a JSON.
3. Ejecutar build: el sistema lee JSON y construye el rig via Python.
4. El rig resultante es idéntico cada vez; reproducible en cualquier máquina.

### IK/FK Match
- Integrado en el Animator Interface; accesible desde el rig publicado.
- Funciona para longitudes de cadena FK arbitrarias.

## Comparación con autorig_tools
El enfoque data-centric de rigamajig2 es más explícito que el de autorig_tools: cada parámetro del rig vive en JSON, lo que facilita el versionado y la colaboración. La arquitectura de componentes con I/O interfaces es conceptualmente similar al patrón modular de autorig_tools pero más formalizado. La diferencia clave es que rigamajig2 separa explícitamente "autor de componentes" de "rigger de personaje", lo cual es útil en equipos grandes pero puede ser overhead en pipeline individual. No documenta explícitamente el uso de matrix nodes vs constraints.

## Takeaways aplicables
- El patrón **JSON data → rig rebuild** es altamente recomendable para autorig_tools: permite versionado git del rig y reproducibilidad en pipeline de producción.
- Formalizar un contrato de I/O para cada módulo (un nodo de entrada, un nodo de salida) simplifica la conexión entre componentes y reduce dependencias internas.
- El uso de **pytest + mayatest** para testing de rigging es una práctica de ingeniería que elevaria la calidad de autorig_tools.
- Separar los tres roles (framework author, rig builder, animator) en interfaces distintas es un patrón de UX escalable.
